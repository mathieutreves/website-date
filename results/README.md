# results/

Committed output of the last full measurement run — `./scripts/validate.sh` for
the dev-split tables, plus the three `--split test` commands listed in the
README's Reproducing section for the held-out ones, which `validate.sh`
deliberately does not run.

These are here so a later reader can diff their numbers against ours rather than
take a table on trust. Each `.jsonl` is the raw per-page record a harness emitted
— `{tool, file, gold, found, ms}` — and each `.txt` is the rendered table. Render
any JSONL yourself with `node scripts/tally.ts <file>`.

Quote the **held-out** figures. The dev split is what the library was tuned
against and its numbers are optimistic by ~7 points; see
[docs/BENCHMARK.md](../docs/BENCHMARK.md).

Two rows that look like they should agree, and do not:

* `permalink-pagedate-TEST.txt` says 88.3%, `permalink-TEST-combined.txt` says
  87.6%. Both are pagedate (standard) on the same 566 pages. `score.ts` blanks
  the dated permalink where the page declares it — `<link rel="canonical">` and
  `og:url` — while the competitor harness blanks every date-shaped path in the
  raw HTML, for every tool alike, because the competitors have no `holdOut`
  mechanism and would otherwise read the label out of an `<a href>`. Quote the
  combined table when comparing tools, `score.ts` for pagedate alone.

`permalink-TEST-combined.txt` is regenerated by `./scripts/score-heldout.sh`,
which renders both harness JSONLs through `scripts/tally.ts` in one table. It used
to be assembled by hand, which meant the one published cross-tool table was the
one file a rerun could not reproduce.

Every `ms/page` column is a median of repeated passes taken after all tools have
been warmed, with the order rotated between rounds. Without that, whichever tool
runs last inherits a warm JIT, and on tools sharing most of their code the bias
is larger than the difference being measured.
